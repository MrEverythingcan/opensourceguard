Token 是什么？
Token 相当于平台发给你的临时钥匙，用来证明“这是你本人的账号”。GitHub 在 Settings → Developer settings → Personal access tokens 里创建，勾选 repo 权限即可；ModelScope 在“账号设置 → 访问令牌”里创建。粘贴后点击同步，就能看到自己账号下的仓库。
① 选择平台② 填 Token③ 同步仓库

整理分两步，安全优先
第一步 Agent 只生成整理方案，一个文件都不会动；你确认后才执行「安全整理」——把临时文件、副本、压缩包移入 .osg_archive 文件夹（随时可搬回来），并补全 .gitignore。代码文件 Agent 不会自动移动，因为会影响 import 路径，这类事会写成建议交给你。

在这里录入问题后，到「维护队列」确认任务状态，再到「修改草稿」运行任务、生成补丁草稿；补丁只生成草稿，人工审核后才决定是否合并。运行失败可以把日志贴到「继续修复」再试一轮。

通过安全校验的问题（Issue）才会进入队列；高风险任务先排队，运行下一项时转人工处理。

任务从哪里来？
① 在「问题修复」页手动录入；② 在 GitHub 仓库设置中配置 Webhook 指向本服务的 POST /github/webhook，新 Issue 会自动进入队列（需配置 OSG_GITHUB_WEBHOOK_SECRET 验签）。带 security、critical 等高风险标签的任务会被拦截并转人工。

修改草稿（Draft PR）

Agent 只生成修改草稿，你审核通过后才决定是否合并，不会直接改动主分支。

这里做什么？
点击「运行下一项」会从队列领取一个排队中的任务并进行分析：返回修复建议与验证状态；验证通过且配置了 GitHub Token 时会生成 Draft PR 草稿等你审核。队列为空时请先到「问题修复」录入。

继续修复

把测试或运行的失败日志交给 Agent，它会分析失败原因，给出下一轮修复计划。

什么时候用这一页？
一次修复验证失败时，把完整的报错堆栈（Traceback）或测试输出贴进来，Agent 会识别失败信号（越界、缺字段、空值、超时等），并给出下一步该改什么。Agent 只给计划，不会自动应用补丁；达到尝试上限会建议人工介入。
① 填问题描述② 粘贴失败日志③ 获取下一轮计划
