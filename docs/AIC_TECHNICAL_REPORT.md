# OpenSourceGuard：面向开源社区的 AI 自动维护与安全修复 Agent

## 1. 问题与场景

开源项目的问题反馈往往停留在 Issue 层面：维护者需要手动阅读描述、在仓库中定位代码、构造复现、判断补丁是否引入回归，再把结果整理成 PR。小型项目缺少专职维护者时，Issue 很容易积压。

OpenSourceGuard 面向开源项目维护者和贡献者，提供一条可审计的辅助维护流程。用户提交 Issue 后，Agent 只处理经过签名验证、风险检查和权限策略允许的事件。

## 2. 方案与创新

项目由五层组成：Webhook 验签层、SQLite 任务队列、混合代码检索层、隔离验证层和 Draft PR 提交层。检索结合词法/BM25 风格评分、路径与符号命中和目录一致性；验证在临时副本中运行，不触碰原始工作树；高风险标签强制转人工。

针对初学者“看不懂仓库”的问题，项目增加仓库解释 Agent：读取 README、许可证、依赖清单、测试目录和部署文件，输出用途、技术栈、适合人群、商用适配度、许可证义务、部署预览和风险提醒。解释结果默认标注为本地分析；如果接入模型，只用于润色，不能替代许可证和安全审查。发现 README、许可证、`.gitignore`、安全说明或最小测试缺失时，Agent 会先列出补齐计划，用户确认后只新增缺失文件，不覆盖已有内容。

0.6.0 增加平台连接层：用户在当前会话填写 GitHub 或 ModelScope Token 后，可以同步账号仓库列表，选择本地项目生成发布预览，并在确认后创建或复用远程仓库、上传项目。GitHub 使用 REST API 和临时凭据助手完成推送；ModelScope 使用官方 `modelscope-hub` 客户端。发布动作与 Issue 自动修复分开，后者仍保持 Draft PR dry-run。

创新点不是“让模型直接改代码”，而是把 AI 生成能力放进一个证据链：Issue → 代码证据 → 最小复现 → 候选补丁 → 基线/候选测试 → 审核草稿。所有自动化动作都能回溯，默认不自动合并。

## 3. AI 与开源融合

AI 用于 Issue 理解、代码检索排序、修复候选生成和测试结果解释；开源资源用于 GitHub/Gitee/GitLab 协作、Python 标准库、公开项目结构和可复用的测试工作流。资源版本、许可证和自主开发边界见 `AIC_RESOURCE_MANIFEST.csv`。

## 4. 实现与验证

当前版本包含 HMAC 验签、Issue 事件归一化、事件去重、原子任务抢占、风险标签拦截、混合检索、临时目录验证、Draft PR dry-run、开源缺项补齐、平台仓库同步和本地 HTTP 演示。测试覆盖签名、去重、风险拦截、检索、隔离验证、补齐动作和发布预览；`scripts/verify_release.py` 会在发布前自动执行这些检查。

本地部署入口只允许生成白名单命令，例如 Python 项目的 `pip install -e .` 或 Node 项目的 `npm install`；默认只预览。实际执行需要 `confirm=true`、`OSG_DEPLOY_ENABLE=1` 和项目路径位于 `OSG_REPO_ROOT` 内，避免把用户输入直接拼接成 shell 命令。

案例使用 `examples/buggy_csv`：基线版本对空输入访问 `rows[0]`，复现测试失败；候选补丁只增加空列表分支，保留单行和多行行为，补丁后复现与全量回归均通过。该案例不连接远程仓库，便于评委独立复现。

## 5. 安全、合规与限制

Webhook 签名在 JSON 解析前验证；`security`、`critical`、`high-risk`、`do-not-auto-fix`、`needs-human` 标签不会进入自动修复；代码执行必须明确选择 `skip`、`local` 或受控 Docker；原仓库不会被自动维护流程直接改写；自动合并被禁止。平台发布必须有用户提供 Token 并点击确认，Token 只在浏览器会话中使用，不写入数据库、提交记录或远程地址。真实部署仍需要维护者配置 HTTPS、GitHub App/Token、沙箱和日志留存。

本项目当前提供可运行原型和本地验证，远程 PR、真实社区收益和大规模模型效果需要在获得仓库授权后单独测量，不能把 dry-run 说成真实线上贡献。
